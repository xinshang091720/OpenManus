## 项目理解分析

对 AIContstructUpdate（AI智建）项目进行了完整代码阅读与理解。

**项目定位**：WPF (.NET 8) 桌面自动更新程序，用于更新 SwarmBIM（蜂群BIM/AI智建）软件。

**核心流程**（MainViewModel 构造函数）：
1. 定位 SwarmBIM 安装路径
2. 调用 InterlinkageGet() 从服务器获取版本信息（JSON），解析"应用中心"插件的下载链接和版本号
3. 备份当前 SwarmBIM 目录到 `<盘符>:\Copy`
4. 删除 Resources 目录（保留 GeneralFile）和含"卸载"字样的文件
5. 检查磁盘剩余空间（需 ≥ 1GB）
6. 在 `<盘符>:\zip`（隐藏文件夹）下载更新压缩包
7. 调用 PulicUpdate() 应用更新

**发现的代码问题**：
- MainViewModel.cs 严重不完整：引用了多个未定义的成员（InterlinkageGet、ApplicationLinks、ReleaseNumber、swarmBIMPath、CurrentFilePath、CopyFilePath、PackagesavePath、PulicUpdate、Progressjd、ProgressNumerical、CloseCommand、CopyDirectory），文件在 110 行处突然结束

- MainWindow_Closed 抛出 NotImplementedException，关闭窗口会崩溃
- 异常处理 MessageBox 标题写成"成功"实为错误提示
- 多余的 using static System.Runtime.InteropServices.JavaScript.JSType

**文件结构**：

## 进度条逻辑实现

用户已重构 MainViewModel.cs（继承 ObservableObject，定义了 Progressjd/ProgressNumerical 属性，新增 LoadLinksConfig/UpdateAi/UpdatePlugin 方法）。

**原问题**：UpdateAi 和 UpdatePlugin 使用 `GetByteArrayAsync().GetAwaiter().GetResult()` 同步下载，阻塞 UI 线程，进度条不更新。

4. 文件复制阶段也加了进度跟踪（按文件数百分比），用 `await Task.Yield()` 让 UI 有机会刷新
5. 移除无用的 `using static System.Runtime.InteropServices.JavaScript.JSType`
6. 修复 catch 块：原标题"成功"改为"错误"

**项目架构变更**：从旧的"服务器 API 获取版本 → 备份 → 清理 → 下载 → 应用"流程，改为读取本地 update_links.json 配置文件获取下载地址，直接下载更新。

## 固化 publish 参数到 csproj

**背景**：用户每次都要输 `dotnet publish -c Release -r win-x64 --self-contained`，太长。

**改动**：csproj PropertyGroup 里加两行：
```xml
<RuntimeIdentifier>win-x64</RuntimeIdentifier>
<SelfContained>true</SelfContained>
```

**效果**：以后改完代码只需 `dotnet publish -c Release` 即可生成单文件 exe。

**注意**：csproj 里固化了 `RuntimeIdentifier=win-x64` 后，普通 `dotnet build` / `dotnet run` 也会带 RID，输出路径会变成 `bin\Debug\net8.0-windows\win-x64\`（多一层 win-x64）。开发调试不受影响，只是路径变了。

## 进度条"卡 99%"问题修复

**用户报告**：解压阶段进度条卡在 99% 不动。

**根因**（3 个问题叠加）：
1. **整数除法丢精度**：`extracted * 100 / totalEntries` 都是 int，1000 个文件解压到 990~999 都显示 99%——10 个文件卡在同一个百分比，视觉上像卡死
2. **进度更新晚于实际解压**：原代码是 `ExtractToFile(...)` 同步执行后才更新进度，最后一个大文件解压期间进度条完全不动
3. **进度文字无阶段名**：直接显示"99%"，用户不知道卡在解压还是复制

**修复**：
- `ProgressNumerical` 改用 `(int)Progressjd`（取浮点进度的整数部分）
- 进度更新移到 `ExtractToFile` 之前，await Task.Yield 后再执行解压
- 文字加阶段前缀和文件计数：`"正在解压... 99% (999/1000)"` / `"正在复制... 50% (50/100)"`
- 下载阶段的进度文字也改用 `(int)Progressjd`

`UpdateAi` 和 `UpdatePlugin` 里的复制阶段同步改了文字（"正在更新..."→"正在复制..."）和整数除法。

## 进度条再次"卡 99%"根因 + 最终修复

**用户报告**：下载阶段卡在 99% 不动（截图：进度条蓝色几乎充满、文字"99%"）。

**先做的验证**：
- `curl -sI http://swarmbim.oss-cn-shenzhen.aliyuncs.com/.../AiConstruction.zip` → `Content-Length: 439468336` ≈ **419 MB**
- `update_links.json` 写了 `AiConstructionLink` 指向该 URL，`ConstructionLink` 为空（所以只走 UpdateAi 流程）

**根因**（与之前 "整数除法丢精度" 的解读不同）：
1. **核心 bug**：`Progressjd = Math.Round(totalRead / totalBytes * 100, 1); ProgressNumerical = $"{(int)Progressjd}%"`
   - **浮点除法**（double）+ **`Math.Round(..., 1)` 保留 1 位小数** + **`(int)` 截断** 三重叠加
   - 最后一帧几乎必然得到 `99.x`（比如 99.931），而 `(int)99.9 = 99`
   - **即使下载真的完成了，UI 也永远显示"99%"**，且 `Progressjd = 99.9` 在 0-100 范围进度条上几乎贴满右边，肉眼就是"99% 满了但卡住"
2. **HttpClient 默认 100s 超时**：对 419 MB 在限速/慢网络下很容易被打断。即使本帧没抛异常，未来大文件场景也是隐患。
3. **下载完成没有 `FlushAsync()`**：buffer 内的字节可能没落盘，下次循环才 push；如果最后一次 ReadAsync 和 dispose 之间出问题，最后几个 buffer 丢失，磁盘上 ZIP 不完整。
4. **解压、复制阶段同样有浮点截断问题**：`(double)extracted/totalEntries * 100` / `(double)(i+1)/totalFiles * 100` 都会在最后一帧卡 99.x。

**修复**（ViewModel/MainViewModel.cs）：
- **下载**：进度数字改 `(int)(totalRead * 100L / totalBytes)`（整数除法，主动 `if (pct > 99) pct = 99` 封顶）；HttpClient 加 `Timeout = TimeSpan.FromMinutes(10)`；循环外 `await fileStream.FlushAsync()` + `Progressjd = 100; ProgressNumerical = "100%"` 兜底
- **解压**：`extracted * 99 / totalEntries` 整数百分比 + 封顶 99；循环外 `Progressjd = 100; ProgressNumerical = "解压完成"`
- **复制（UpdateAi + UpdatePlugin）**：`(i+1) * 99 / totalFiles` 整数百分比 + 封顶 99；循环外 `Progressjd = 100; ProgressNumerical = "复制完成"`
- **MainWindow_Loaded 兜底**：成功 `ProgressNumerical = "更新完成"`；失败 `Progressjd = 100; ProgressNumerical = "更新失败"`（即便异常路径也不再卡 99%）

**核心思路**：所有 3 个阶段都遵循"循环内**封顶 99** + 循环外**强制 100%**"——封顶避免浮点截断永久停在 99.9，外置的 100% 让"到顶"成为显式语义，不会被微小计算误差搞丢。

**验证**：
- `dotnet build -c Release` → 0 警告 0 错误
- `dotnet publish -c Release` → `bin\Release\net8.0-windows\win-x64\publish\AIContstructUpdate.exe`（72MB，15:49 重新生成）

## 后台线程 + 批量 Dispatcher UI 更新

**用户反馈**：下载到55%后进度条卡住不动，解压和复制期间完全没反应。根因是解压用了一次性 `ExtractToDirectory`（后台线程无进度反馈），复制时 `Task.Yield()` 在 UI 线程上阻塞执行 File.Copy 导致消息泵没机会刷新。

**方案**：解压和复制都放后台线程（`Task.Run`），每 `total/40` 个文件通过 `Application.Current.Dispatcher.Invoke` 批量更新 UI。约 40 次 UI 刷新，既轻量又能让进度条真实推进。

**新增方法**：
- `ExtractWithBatchedProgressAsync(zipPath, destDir, basePct, rangePct)` — 后台逐文件解压 + 批量 Dispatcher.Invoke
- `CopyWithBatchedProgressAsync(sourceDir, targetDir, basePct, rangePct)` — 后台逐文件复制 + 批量 Dispatcher.Invoke

**权重调整**：下载 0→55 / 解压 55→82 / 复制 82→100（更贴合实际耗时比例）。
